── Part 6: ZKP + TEE — Complementary, Not Competing ──

    Each layer covers the other's blind spots:

    Threat                           ZKP alone    TEE alone    ZKP inside TEE
    ─────────────────────────────────────────────────────────────────────────
    Verifier learns GPS              ✅ hidden    ❌ output    ✅ hidden
    Kernel 0-day reads GPS           ❌ ptrace    ✅ encrypted ✅ both protect
    TEE side-channel leaks data      n/a          ❌ Spectre   ✅ proof only
    Fake GPS from compromised OS     ❌           ⚠ ecalls*   ⚠ ecalls*

      * SR-IOV / VFIO passthrough can give enclave direct sensor access,
        bypassing the OS — same input integrity iLO7 gets architecturally.
        Requires: IOMMU + SR-IOV-capable sensor hardware + driver in enclave TCB.

    ⚠ Neither ZKP nor TEE protects against RCE inside the execution environment
      Buffer overflow in enclave → attacker runs IN the trust boundary
      TEE attestation only measures code at load time, not runtime integrity
      Same limitation as Linux IMA — load-time measurement, not runtime

    Where to run the ZKP prover:

    Option 1:  Userspace sidecar      (today's POC — portable, fast iteration)
    Option 2:  SGX/SEV enclave         (runtime isolation, but shared CPU → side-channels)
    Option 3:  Management processor    ← Strongest
             (iLO7)

    Why iLO7 is the strongest TEE:
    • Separate silicon   — own ARM CPU, own RAM → no shared microarchitecture
    • No side-channels   — physically different processor → Spectre irrelevant
    • Direct sensor access — GPS data never transits host OS → input integrity solved
    • Silicon Root of Trust — HPE-signed firmware, not Intel/AMD microcode

    SGX is a locked room on a shared floor.
    iLO7 is a separate building.
